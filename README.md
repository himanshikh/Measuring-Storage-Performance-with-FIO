# CS559 Lab 10: Measuring Storage Performance with FIO

## Overview

This lab focuses on measuring storage performance using **Flexible I/O Tester (FIO)**. The aim is to understand how different storage workloads and queue depths affect I/O performance.

The experiments were performed using FIO inside an Ubuntu 24.04 virtual machine running through UTM on an Apple M1 MacBook.

PostgreSQL was selected as the reference database. FIO was used to simulate storage access patterns that represent common database operations. No actual PostgreSQL queries were executed.

## Objectives

- Measure storage performance using IOPS, bandwidth and latency.
- Compare random and sequential read operations.
- Study the effect of different queue depths.
- Understand the performance impact of read/write workloads.
- Analyse P95 and P99 latency.

## Experimental Environment

| Component | Configuration |
|---|---|
| Host Machine | MacBook Air, Apple M1 |
| Host OS | macOS 13.5 |
| Virtualisation | UTM with QEMU 9.1 |
| Guest OS | Ubuntu 24.04 LTS |
| FIO Version | 3.36 |
| I/O Engine | libaio |
| Test File Size | 1 GiB |
| Runtime | 45 seconds per run |
| Ramp-up Time | 5 seconds |
| Number of Repetitions | 3 |
| Queue Depths | 1, 8, 32 |

## Workloads

Four workload cases were tested:

| Case | I/O Pattern | Block Size | Read/Write Ratio |
|---|---|---|---|
| A | Random Read | 4 KiB | 100% Read |
| B | Random Read/Write | 4 KiB | 70% Read, 30% Write |
| C | Random Read/Write | 8 KiB | 30% Read, 70% Write |
| D | Sequential Read | 256 KiB | 100% Read |

Each workload was tested at queue depths of 1, 8 and 32, with three repetitions for each configuration.

This resulted in a total of **36 experiments**.

## Metrics Collected

The following performance metrics were collected from the FIO JSON output:

- **IOPS:** Number of input/output operations completed per second.
- **Bandwidth:** Amount of data transferred per second.
- **Average Latency:** Average time taken to complete an I/O operation.
- **P95 Latency:** Latency below which 95% of operations completed.
- **P99 Latency:** Latency below which 99% of operations completed.

## Running the Experiments

Make sure FIO is installed on Ubuntu.

Install FIO using:

```bash
sudo apt update
sudo apt install fio -y
```

Create the experiment directory and place the four job files (`caseA.fio`, `caseB.fio`, `caseC.fio`, and `caseD.fio`) inside it.

Create a directory for storing the results:

```bash
mkdir -p "$HOME/Lab10_FIO_Results/results"
```

Run the experiments using:

```bash
chmod +x "$HOME/Lab10_FIO_Results/run_lab.sh"
bash "$HOME/Lab10_FIO_Results/run_lab.sh"
```

The script executes all four workloads at queue depths 1, 8 and 32, with three repetitions. Each experiment generates a separate JSON output file.

## Results

All 36 experiments completed successfully.

The results were analysed using the generated JSON files. The report includes the average IOPS, bandwidth, average latency, P95 latency and P99 latency for each workload and queue-depth combination.

The experiments showed that:

- Random reads achieved a higher number of I/O operations per second.
- Sequential reads achieved much higher bandwidth because of their larger block size.
- Increasing queue depth did not always improve performance.
- The write-heavy workload showed higher tail latency than the read-heavy workload.

Refer to the lab report for the detailed result tables and analysis.

## Limitations

- The experiments were performed inside a virtual machine, so the results may differ from those obtained on a physical Linux machine.
- FIO generates synthetic file I/O workloads and does not execute SQL queries.
- Actual database behaviour also depends on caching, query execution, transactions and other database operations.
- The results represent the storage performance of the tested virtualised environment.

## Conclusion

This lab helped compare different storage access patterns and understand the effect of queue depth on storage performance. It also demonstrated why IOPS, bandwidth and latency should be considered together when evaluating storage systems.

FIO provides a useful way to simulate storage workloads, although it cannot fully reproduce the internal behaviour of a database.
